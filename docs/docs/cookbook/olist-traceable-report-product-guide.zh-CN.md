# Olist 可追溯经营分析报告产品说明

## 1. 产品概述

Olist 可追溯经营分析报告面向需要回答“数字从哪里来、图表如何生成、结论依据是什么、数据变化后如何复查”的业务分析场景。

它不是单纯的聊天回答，也不是把 SQL 日志附在报告末尾。报告中的经营指标、数据表、图表和数值结论都可以点击打开证据抽屉，回溯至本次实际执行的 SQL、Python 计算、原生图表、知识库口径或上游数据产物。

Olist 是用于演示的巴西电商数据集。默认业务口径为：已交付订单、商品 GMV 不含运费、币种为巴西雷亚尔（R$）。具体定义见 Olist 指标治理知识库。

## 2. 解决的业务问题

| 常见问题 | 产品如何回答 |
| --- | --- |
| “GMV 为什么是这个数字？” | 点击 KPI 数值，查看 SQL、过滤条件、数据源、结果快照和执行步骤。 |
| “这张趋势图依据什么？” | 点击图表右上角证据标识，查看 Chart、对应 SQL 和数据结果。 |
| “这个结论是模型猜的吗？” | 点击结论中加粗的数值，查看支撑该数值的最小证据集合。 |
| “GMV 是否包含运费？” | 查看 KB 证据或 Olist 口径：商品 GMV 为 `SUM(order_items.price)`，运费单独计算。 |
| “数据更新后能否重新分析？” | 保留报告运行、数据源和产物依赖；刷新能力以新 revision 重跑为目标，历史结果不被覆盖。 |
| “为什么报告没有生成？” | 界面保留真实执行状态。分析未完成、模型格式错误或证据绑定失败时不会伪造报告成功。 |

## 3. 用户角色与使用方式

### 3.1 业务负责人

业务负责人输入自然语言问题，阅读报告，点击关键数字和结论查看证据，不需要写 SQL、Python 或图表类型。

### 3.2 数据分析师

分析师查看 SQL、数据快照、计算过程和证据图谱，判断口径是否正确、是否存在多表连接导致的重复计算，并定位需要复跑的步骤。

### 3.3 平台管理员

管理员配置数据源、模型代理、知识库和权限；管理密钥；运行回归测试；监控报告生成失败、图表渲染失败与刷新状态。

## 4. Olist 数据与默认口径

### 4.1 分析范围

- 默认订单状态：`delivered`；
- 默认时间字段：订单购买时间；
- 默认货币：BRL/R$；
- 默认订单量：`COUNT(DISTINCT order_id)`；
- 默认商品 GMV：`SUM(order_items.price)`，不含运费；
- 默认客单价：商品 GMV / 已交付订单量；
- 默认运费占比：总运费 / 商品 GMV。

### 4.2 重要口径提醒

支付金额、商品 GMV、含运费成交额是不同概念。报告中如果使用 `payment_value`，必须称为“支付金额”；如果使用 `price + freight_value`，必须称为“含运费成交额”，不能误标为 GMV。

订单明细、支付记录、评价记录具有一对多关系。需要同时分析商品、支付和评价时，应先分别聚合到订单粒度，再关联，避免 GMV 或订单数被重复放大。

## 5. 推荐的真实用户提问

用户无需在提问中要求“SQL 证据”“Python”或“图表绑定”。以下示例均应由系统自行完成分析与证据链构建。

### 5.1 综合经营诊断

> 请分析 Olist 在 2017 年 1 月至 2018 年 8 月已交付订单的经营表现。说明商品 GMV、订单量、客单价、运费占比和月度趋势；比较主要品类和客户州；分析配送时长、逾期交付与评分的关系，以及支付方式和分期情况。最后给出三条可执行的经营建议。

预期报告应包含：总体 KPI、月度趋势图、品类/地域/履约/支付分析、三条建议，以及每个关键对象的证据入口。

### 5.2 履约与满意度专题

> 请找出 Olist 客户评分偏低的主要运营因素，重点比较准时和逾期订单的配送时长、评分和订单占比，并按客户州识别优先改善区域。给出两条有优先级的履约改善建议。

该问题通常会触发订单日期计算、分组统计和图表；如需相关性、异常点、分布或复杂派生计算，系统可自行调用 Python。

### 5.3 品类增长专题

> 请分析 2018 年上半年商品 GMV 前十品类的增长、订单量、客单价和评价表现，识别高增长但评分偏低的品类，并给出选品和服务优化建议。

### 5.4 指标口径专题

> 本报告里的 GMV、客单价和运费占比具体如何计算？请按 Olist 数据模型解释，并用当前数据验证结果。

该问题适合同时使用知识库与 SQL：知识库解释定义，SQL 验证实际数值。两类证据在报告中应分别展示。

## 6. 报告阅读指南

### 6.1 KPI 和表格

KPI 卡片、表格右上角或数值附近的 `SQL`、`PY`、`KB` 标识表示可回溯证据。

- `SQL`：数值直接来自查询；
- `PY`：数值或可视化经过 Python 计算；
- `图`：来自原生 Chart 或 Python 生成图像；
- `KB`：使用了知识库的口径、规则或业务资料。

点击数值时，优先查看该数值本身绑定的证据，而不是整个页面的所有执行记录。

### 6.2 图表

图表右上角的证据入口可以显示：图表名称、执行状态、关联查询、数据源、图表 spec 或 Python 代码、结果快照和“定位到执行步骤”。

图表可能来自两类实现：

1. **原生图表**：由 DB-GPT 原生 ChartAction 根据 SQL 结果生成，支持结构化图表数据；
2. **Python 图像**：用于统计分布、复杂计算或专用可视化，显示其 Python 上游证据。

服务端显示的图表规格生成耗时不等于浏览器绘制耗时；Python 派生图片也不应被误解为独立图表执行耗时。

### 6.3 结论和建议

报告中的结论数值应加粗或以可点击样式展示。例如“SP 州贡献 **38.36%** 商品 GMV”中的 `38.36%` 可独立打开证据抽屉。

建议的正确表达应包含行动、对象和依据，例如：

> 优先优化逾期订单占比较高的区域配送承运商和承诺时效，因为逾期订单的平均评分明显低于准时订单。

其中“逾期订单占比”“平均评分差异”等数值均应能回溯。业务解释若来自知识库或外部资料，也应带 KB/引用证据。

## 7. 证据抽屉中应看到什么

| 证据类型 | 抽屉内容 | 用途 |
| --- | --- | --- |
| SQL | 查询语句、数据源、执行状态、耗时、结果快照 | 核验指标、表格、分组结果 |
| Python | 代码、运行输出、输入依赖、生成文件 | 核验计算、统计检验、复杂图像 |
| Chart | 图表信息、结构化 spec、上游 SQL | 核验原生图表来源 |
| KB | 来源名称、引用片段、检索位置 | 核验指标口径、规则与业务解释 |

如果一个图表来自 SQL 结果再由原生 ChartAction 渲染，证据链应为：

```text
报告图表
  -> ChartArtifact
  -> SQLArtifact
  -> 数据源
```

如果一个结论使用 Python 在 SQL 数据上计算，则链路应为：

```text
结论中的数值
  -> PythonArtifact
  -> SQLArtifact
  -> 数据源
```

## 8. 证据图谱

“证据图谱”以结论为起点，展示 claim 到 SQL、Python、Chart、KB artifact 的关系，以及 artifact 的上游依赖。

图谱用于回答：

- 哪些结论依赖同一条 SQL？
- 哪张图来自哪个查询？
- 哪些结论只使用了口径资料但没有数据证据？
- 数据源变化时，哪些报告对象可能受影响？

同名且证据集合相同的展示节点会去重。重复的标题、表格单元格和数值 span 不应制造重复的结论节点。

## 9. 报告成功标准

一份可交付的 Olist 报告至少满足：

- 有明确的时间范围、订单状态、货币和指标口径；
- KPI、表格、图表和关键数值结论均具备证据入口；
- 图表真实渲染，不以空白区域、损坏图片或编辑控件替代；
- 图表与表格的证据各自绑定，图表不会覆盖表格或产生重复控件；
- 若用户要求固定数量建议，报告包含该数量的可执行建议；
- 未完成或失败时显示真实状态，不产生空报告链接；
- PDF 导出包含当前已渲染的图表。

## 10. 已知边界

1. 知识库只有在系统实际检索并引用时才会显示 KB 证据；并非每次分析都会自动使用。
2. 知识库可解释口径，但不能替代 SQL 对具体数值的支撑。
3. 相关性、趋势和分组差异不能直接写成因果关系；缺少外部证据时，应明确是业务假设。
4. 目前具备报告 revision 与依赖信息；全自动增量刷新仍需后续完善，不应假设任意历史报告都能无条件一键重算。
5. 历史报告没有原生 Chart spec 时可以查看证据，但不应伪造可交互图表。
6. 报告不提供 Markdown 导出；使用 HTML 预览和 PDF 打印。

## 11. 常见问题

### 为什么没有看到 KB 标识？

可能原因是本次问题只需要数据库查询，Agent 没有检索知识库；也可能是检索到了资料但没有把其用于报告中的口径或结论。提出“按 Olist 指标口径解释并验证”这类问题更容易触发 KB 与 SQL 的组合使用。

### 为什么报告没有生成？

查看执行步骤。常见原因包括模型输出不符合工具协议、任务在分析阶段提前结束、HTML 报告没有通过证据绑定校验、数据源或模型服务不可用。系统应显示实际失败原因，而不是显示一个空的报告页。

### 为什么图表有证据但没有显示？

先确认 ChartArtifact 为成功状态并有有效 chart spec 或图片文件；再检查报告容器、浏览器网络请求和前端图表渲染。图表不能仅凭 artifact 存在就假定已绘制成功。

### 为什么支付金额与商品 GMV 不一致？

两者口径不同。商品 GMV 是商品 `price` 的总和；支付金额来自 `payment_value`，可能受支付记录和口径差异影响。报告必须使用准确名称，不能混写。

## 12. 演示验收清单

1. 挂载 Olist 数据库和 Olist 指标治理知识库。
2. 输入“综合经营诊断”示例，不在 prompt 中加入任何证据、SQL 或图表技术约束。
3. 确认执行步骤中出现实际 SQL；复杂场景可出现 Python/Chart/KB。
4. 在分析报告中检查 KPI、趋势图、表格、结论和三条建议。
5. 点击至少一个 SQL KPI、一个图表、一个结论数值；确认抽屉显示对应 artifact 和上游依赖。
6. 若报告实际使用知识库，点击 KB 标识并确认显示引用来源。
7. 打开证据图谱，确认没有同一结论的大量重复节点。
8. 导出 PDF，确认已渲染的图表出现在 PDF 中。
